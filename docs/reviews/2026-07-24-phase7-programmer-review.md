## Summary

The placeholder-shape fallback wiring is careful, the `styleable()` duck-type guards are correctly placed so **nothing crashes when real art lands** (I traced all four render loops — no shape-only method escapes its guard onto a Sprite), the Preload scene degrades gracefully on 404 and can't get stuck, `window.__game` collides with nothing, the fx→sound map is complete against all 11 live server fx types, and the phase-machine wave semantics the wave-preview depends on are read correctly (during BUILD, `state.wave` is the *upcoming* wave, so the gate telegraph fires on the right wave). No CRITICAL, no crash, no server touch.

But three things are wrong in ways the green suite is structurally blind to, and one of them defeats this phase's own central design promise:

1. **The "drop real art in with zero other code change" contract is false for enemy/player status feedback.** The instant a texture key is populated, every per-frame status telegraph that lives in a `styleable()`-guarded branch silently stops rendering — aggro rings, root/freeze rings, the elite gold ring, and the downed-vs-reviving color — because the Sprite branch has no `setTint`-based equivalent. Art arrives, readability regresses, and the contract told everyone not to look.
2. **`SAME_TYPE_CAP = 2` is inert.** `playFx`'s 80 ms per-name floor already collapses same-name plays inside a synchronous batch (and across 50 ms snapshots) to ≤1 audible. The cap can be 2, 5, or 99 with identical audible result. The test can't see this because `logPlay` runs *before* the rate-limit return, so the log counts attempts, not sounds.
3. **The wave-preview swatch/label alignment is a latent mislabel** driven by `.filter(Boolean)` compaction against positionally-fixed swatch colors. Dormant for the current `WAVES` (only the *trailing* troll is ever absent), it mislabels the moment a comp omits a leading/middle type — the precise "add a wave via balance.js" drop-in this UI is built around.

Ranked most-severe first.

## HIGH

- **H1 — Real art silently kills every enemy and player status telegraph; the "zero-code-change art drop-in" contract is false.** `client/src/render/sprites.js:24` `styleable()` returns true only for shape fallbacks (`setStrokeStyle` present). In `GameScene.js` the enemy loop (`:346-358`) puts *all* status visuals inside `if (styleable(entry.dot)) { setRadius; elite gold ring; aggro red ring; root/freeze cyan ring } else { setScale(elite?1.4:1) }`. The `else` (real-Sprite) branch conveys elite-by-size only — **AGGRO, ROOT, and FREEZE become invisible, and the elite gold ring is gone.** The player loop (`:292-298`) is the same shape: the downed/reviving stroke (`reviving ? green : red`) is skipped for Sprites, so an art-backed downed player shows alpha 0.45 but loses the green-vs-red reviving distinction. Only `setAlpha(SLOW)` survives (it's outside the guard). **Why it breaks:** these are gameplay-relevant reads — aggro tells you which enemy is on a teammate, root/freeze tells you a CC landed, reviving-green tells you someone's already channeling a pickup. The manifest comments (`sprites.js:1-12`, `manifest.js:5`) promise "filling this in is the ONLY change needed"; it is not — the Sprite path needs `setTint`/overlay equivalents for each of those states, and there is no TODO marking the gap. Because the contract says "no re-review needed," this ships broken and unnoticed when the project owner drops art in weeks later. **Also inconsistent within H1:** elite sizing is `base.r + 3` in the shape branch (goblin 7→10 = ×1.43, orc 9→12 = ×1.33, troll 12→15 = ×1.25) vs a hardcoded `×1.4` in the Sprite branch — troll elites jump noticeably larger when art lands.

## MEDIUM

- **M2 — `SAME_TYPE_CAP = 2` is dead logic; `playFx`'s 80 ms per-name limiter already caps same-name audible plays at 1 per batch, and the test can't detect it.** `audio.js:204-216` counts each fx type per batch and lets 2 through to `playFx`; `playFx` (`:188-198`) drops any call within 80 ms of the last same-name play. A snapshot batch runs synchronously (`consumeServerFx` is a tight loop), so `Date.now()` is identical for every call in it — the 2nd `enemy_hit` is 0 ms after the 1st and is **always dropped**. Worse, at 20 Hz (`NETCODE.SNAPSHOT_EVERY_N_TICKS: 3` → 50 ms snapshots) even the *first* same-name play of a batch is dropped when the prior snapshot also fired it (50 < 80), so sustained combat sounds land at ~10 Hz regardless of `SAME_TYPE_CAP`. Net: the cap has **zero audible effect** at any value ≥1. It reads as a reasoned per-batch mixer control; it is a carryover that the 80 ms floor renders inert. The green test (`audioMap.test.js:58-71`) asserts `dmgs == SAME_TYPE_CAP` — but it measures `window.__audioLog`, and `logPlay` (`playFx:190`) runs *before* the 80 ms return, so the log records both attempts even though only one would sound. The assertion is satisfied by log-counting, not by audio, so it can never catch that the cap does nothing. Decide the real intent: if you want N simultaneous same-type hits to actually stack/thin audibly you need per-play mixing, not a count the rate-limiter eats; if you don't, delete the cap and keep only the 80 ms floor.

- **M3 — Wave-preview swatch color / label misalignment, latent under current `WAVES`.** `wavePreview.js:17-19` builds `lines` by mapping the fixed order `[goblin, orc, troll]` then `.filter(Boolean)`, which *compacts* the array. `createWavePreview.update` (`:58-62`) then assigns `preview.lines[i]` to `swatchRows[i]`, whose swatch **color is hard-bound to enemy index** `ENEMY_BASE[i]` (`:36`, 0=goblin/green, 1=orc, 2=troll). For a comp with a zero/absent *leading or middle* type — e.g. `{ goblin: 0, orc: 5, troll: 2 }` or `{ orc: 5, troll: 2 }` — `lines` compacts to `["Orc x5","Troll x2"]`, so the **green (goblin) swatch gets labeled "Orc x5"** and the orc swatch "Troll x2". Traced against `shared/balance.js:88-102`: every current wave includes goblin and orc, and only the *trailing* troll is ever missing (`{goblin:6, orc:2}` compacts correctly because the hole is last), so the bug **does not fire today**. It fires the first time balance gets a comp that drops a non-trailing type — exactly the "add waves via `balance.js` with no code change" path the module advertises (`wavePreview.js:3-4`). Fix by indexing labels by type position (build `lines` as a length-3 array with `''` holes and let the per-row visibility toggle hide empties) rather than compacting.

## LOW

- **L1 — Optimistic build/sell sfx fire before the server confirms, so rejected placements still thunk.** `GameScene.js:119,122` play `sell`/`build` synchronously in `pointerdown`, before the `BUILD_STRUCTURE`/`SELL_STRUCTURE` round-trip. A build on an invalid tile or with insufficient gold plays the build sound, then `STRUCTURE_REJECTED` arrives — audio says "placed," reality says "no." Conversely there is no *server* fx for build/sell, so a teammate's successful build is silent to you while your own *rejected* build is audible. Either gate the sfx on server ack or accept the optimism and document it.

- **L2 — `window.__audioLog` overcounts; the advertised "text-verification path" records inaudible plays.** `playFx` logs at `:190` *before* the 80 ms rate-limit (`:193`), the `_ready` check, and the `_muted` check (`:195`). So the log the module docstring calls "what the test suite checks" (`audio.js:9`) counts rate-limited, not-yet-loaded, and muted attempts as if they sounded. Any current or future verification built on `__audioLog` overstates real audio. If the log is meant to prove *audibility*, move `logPlay` past the guards (and accept it goes quiet pre-`_ready`); if it's meant to prove *intent*, document that explicitly so no one trusts it for output.

- **L3 — The Preload scene-order change and its 404 degradation path are entirely unit-untested.** `main.js:14` now boots `scene: [Preload, GameScene]` (previously GameScene-first); `Preload.create` (`:51-58`) always `scene.start('GameScene')` so it can't get stuck, and `loaderror → _failedKeys → skip buildAnimsForAtlas` (`:45-53`) is sound reasoning — but the added test never instantiates Phaser, so none of this boot-path change is covered by the suite. The empty-manifest case is trivially fine; the partial-asset case (PNG loads, JSON 404s → frameless texture, `textures.exists` may return true, sprite renders as one un-animated frame) is reasoned-correct only. Worth one e2e/manual boot before real assets land.

- **L4 — Dead symbols.** `elementTint` is imported in `GameScene.js:21` and never used (per-element atlases via `ELEMENT_ATLAS_KEY` made it moot); `entitySprite`'s `tint` param (`sprites.js:13`) is passed by no call site for the same reason; `ui_click` is declared in `SFX_NAMES`/`SFX_VOL` (`audio.js:23,33`) but played nowhere. Harmless, but each is a small "is this wired up?" trap for the next reader. Prune or wire.

## What I checked and found sound

- **fx→sound map is complete.** Grepped every `state.fx.push({ type })` across `server/game/*.js`: exactly 11 types (`swing, projSpawn, boom, ability, ability2, dmg, pdmg, downed, pdied, revived, respawn`) — all 11 are in `FX_MAP`. No server fx is silently unmapped *today*. (The exhaustiveness is unenforced, though — a future server fx type will pass the whole suite with no sound; the test hardcodes the same 11-element list rather than importing the live set.)
- **No runtime crash when art lands.** Traced all four render loops: every `setStrokeStyle`/`setRadius`/`setFillStyle` is inside a `styleable()` guard or on a hardcoded-fallback path (projectiles pass `key: null`, always Arc); `setPosition/setVisible/setAlpha/setDepth/setScale` all exist on Phaser Sprite. The failure mode of real art is *missing telegraphs* (H1), not exceptions.
- **Wave-preview gate semantics are correct.** `startBuildPhase(state, wave)` (`phaseMachine.js:26-29`) sets `state.wave` to the *upcoming* wave and `state.wavePlan = WAVES[wave-1]`; the waveEnd→build transition passes `state.wave + 1` (`:120`). So `phaseInfo.wave` during BUILD is the wave about to be fought, and `gateOpens = SIDE_A===wave || SIDE_B===wave` telegraphs on the correct wave (SIDE_A on the build before wave 4, SIDE_B before wave 7). The prior session's comment was right; I verified against source. (Minor: CENTER (wave 1) is intentionally not telegraphed — it's the start gate.)
- **`window.__game` collides with nothing.** Grepped `client/src` + `server`: no other `__game`/`window.game`; it matches the existing `__net`/`__scene`/`__audio` debug-handle convention.
- **Music reconcile ordering is correct.** `PHASE_CHANGE` computes `enteringFight` from the *old* `phaseInfo` before reassigning, and `reconcileFromPhase(p.phase)` reads the payload directly (not `this.phaseInfo`), so the assignment order is immaterial; no double-fire of `wave_start` (guarded by prev-phase). `consumeServerFx` and the visual `_playFx` loop are separate passes over the same fx array — no double audio.
- **Preload can't hang.** `create()` unconditionally starts GameScene; all-atlases-fail still boots to placeholder shapes.

## Verdict

**GO WITH NOTES.** Nothing here blocks committing the scaffolding — it's client-only as claimed, it can't crash, and with the empty manifest it's behavior-neutral today. But H1 must be logged as a hard prerequisite on the *art-drop* task, not this one: the phase's headline promise ("drop a key in, zero code change") is false for enemy/player status feedback, and the way it's written guarantees no one re-checks. M2 and L2 are the same root defect — `logPlay` sits above the rate-limiter, so the cap is inert *and* the test that would police it is measuring the wrong thing; fix the ordering and decide whether the cap earns its keep. M3 is a genuine latent mislabel that the "waves are pure data" design will trip. The LOWs are cleanup. The `styleable` guard discipline and the Preload/scene-order degradation are the strongest parts and I could not break them.
