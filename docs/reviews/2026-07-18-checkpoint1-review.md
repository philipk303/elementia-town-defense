## Findings

- **C1 (CRITICAL): a socket already in a room can create/join more rooms, permanently leaking room slots — 3 unauthenticated messages brick the whole server.** Neither `createRoom` (`server/rooms/index.js:59`) nor `joinRoom` (`server/rooms/index.js:86`) nor the handlers (`server/index.js:74`, `server/index.js:85`) check `socketToRoom.has(socket.id)`. `socketToRoom.set` (`server/rooms/index.js:157`) silently overwrites the old mapping, so the first room keeps a "human" slot whose socketId is unroutable forever. **Failure scenario (reproduced against the live module):** one socket emits `CREATE_ROOM` twice → both cap slots consumed; on disconnect, `leaveRoom` only cleans the *second* room; the first room survives with a phantom human, `rooms.size` stays 1, and it can never be freed (its only "human" can never disconnect again). Repeat once more from a second socket → `MAX_CONCURRENT_ROOMS=2` is permanently exhausted; every future `CREATE_ROOM` returns "Server at capacity" until process restart. Variant: emitting `JOIN_ROOM` for your own room adds a *duplicate player with the same socketId* and steals a second element slot. This defeats the CP0 M4 room cap it sits ten lines above. **Fix direction:** at the top of `createRoom`/`joinRoom`, reject (or auto-leave) if `this.socketToRoom.has(socket.id)`; add a regression test for double-create and self-join.

- **H1 (HIGH): host leaving the lobby bricks the room — `hostId` dangles and there is no host migration.** `leaveRoom`'s lobby path (`server/rooms/index.js:193-203`) splices the host's slot out but never reassigns `room.hostId`; `REQUEST_START` gates on `caller.id !== room.hostId` (`server/index.js:134`). **Failure scenario:** Alice creates a room, Bob and Cara join, Alice's tab crashes → the room persists (humans remain) but *nobody* satisfies the host check; the Start button is hidden for everyone (`client/src/main.js:58`) and the lobby is dead weight against the 2-room cap until every human gives up and leaves. **Fix direction:** on host removal, promote the earliest-joined remaining human to `hostId` and broadcast the change (client re-evaluates Start-button visibility).

- **H2 (HIGH): the "60 Hz" loop is an unverified assumption — measured ~35 Hz on the dev box, and the accumulator-free `setInterval` never compensates.** `startLoop` schedules `setInterval(..., CONFIG.TICK_MS)` with `TICK_MS = 16.67` (`server/game/loop.js:25-68`); on this Windows dev machine 120 ticks took 3,435 ms (**28.6 ms/tick ≈ 35 Hz**, Windows timer coarseness — `setInterval(16)` measures the same). Phase clocks survive because they consume real `deltaMs`, but everything *tick-count-derived* silently rescales: `SNAPSHOT_EVERY_N_TICKS=3` means the "20 Hz" broadcast is actually ~11.6 Hz in dev and ~19.6 Hz on Linux — the client interpolation layer (Phase 4, `INTERP_DELAY_MS=100`) will be tuned against whichever cadence the dev box happens to produce. Worse, larger real ticks mean larger per-tick displacements in Phase 3: the CP0 C1 tunneling analysis was calibrated at ~30 px/tick under a 16.7 ms tick; at 28.6 ms the same velocities produce ~1.7× the displacement and the anti-tunneling margins shrink accordingly. Spec §5 mandates the 60 Hz sim as a *correction* of a prior factual error, so shipping a loop that doesn't achieve it — with the real-hardware validation (CP0 M3) deferred to Phase 8 — is compounding unvalidated assumptions. **Fix direction:** measure and log actual achieved tick rate at loop start; either drive the loop with a drift-compensating scheduler (setTimeout chain aiming at `nextTickAt`) or explicitly document/store the achieved Hz so Phase 3/4 constants are derived from measured cadence, not the constant.

- **H3 (HIGH): reconnect-token replay while the slot is still connected silently hijacks it — and the realistic trigger is a user duplicating a tab.** `reconnect` (`server/rooms/index.js:277-299`) never checks `player.socketId !== null`; it overwrites `socketId` with the new socket's id. `sessionStorage` is *copied* on browser tab-duplication and session-restore, and `network.js` auto-emits `RECONNECT_TOKEN` on every connect when a token exists (`client/src/network.js:50-51`). **Failure scenario:** mid-match, the player duplicates their tab (or the browser restores the session in a second window) → the new tab's connect auto-replays the token → the server rebinds the slot to the new socket; the original tab still *looks* connected but every `SET_READY`/future input fails the `p.socketId === socket.id` lookup (`server/index.js:141`) and is silently dropped — a zombie client that still receives full snapshot egress. When the zombie socket finally disconnects, `leaveRoom` finds the room via `socketToRoom` but no player matches, and returns at `server/rooms/index.js:189-190` **before** the `socketToRoom.delete` on line 191 — a permanent stale map entry per occurrence. **Fix direction:** in `reconnect`, if `player.socketId` is set, force-disconnect/unbind the old socket first (and delete its `socketToRoom` entry); in `leaveRoom`, delete the `socketToRoom` entry before the player-lookup early returns.

- **M1 (MEDIUM): `deltaMs` comes from non-monotonic `Date.now()` and is unclamped in either direction — a backward clock step *inflates* phase clocks; a forward jump skips whole phases.** `loop.js:26-28` computes `deltaMs = now - lastTickAt`; `tickPhaseClock` does `Math.max(0, clock - deltaMs)` (`server/game/phaseMachine.js:41-43`), so a negative delta (NTP step-correction, VM clock slew on free-tier hosts) *adds* to `phaseClockMs`/`fightClockMs` — a −30 s step mid-build makes a 45 s build timer a 75 s one; the stub fight clock likewise. A large forward jump (host suspends the laptop, Render instance migration) delivers one tick with `deltaMs` = minutes: a `fixed`-style build phase completes instantly with zero build time, or waveEnd + the next build's whole timer semantics collapse into single-tick jumps. **Fix direction:** use a monotonic source (`process.hrtime.bigint()`/`performance.now()`) and clamp `deltaMs` to `[0, ~250 ms]` per tick.

- **M2 (MEDIUM): phase-machine tests exercise a *different* `players` shape than production, on the strength of a false comment.** `test/game/phaseMachine.test.js:10-11` says the factory's keyed object "mirrors createGameState's keyed-object shape" — it does not: `createGameState` builds an **array** (`server/game/state.js:36,67`). The machine only works on both by accident (`for (const id in state.players)` at `phaseMachine.js:30` iterates array indices; `Object.values` at `:48` tolerates arrays). Any future phase-machine code written against the tests' shape — e.g. `state.players[playerId]` keyed by id, the natural reading of that comment — passes the whole unit suite and breaks in production (`ready` never resets for real players → ready-style build never completes after wave 1). **Fix direction:** make the test factory produce an array matching `createGameState`, fix the comment, and change `phaseMachine.js:30` to `for (const p of state.players)`.

- **M3 (MEDIUM): solo start is allowed but spec §1 says "2–4 human players" — a spec deviation with no dated amendment.** `REQUEST_START` (`server/index.js:130-136`) lets a lone host start with 3 bots; nothing enforces a 2-human minimum and the smoke/room tests never assert one either way. The standing rules (`docs/plans/2026-07-18-slice1-implementation-plan.md`, "Standing rules for execution") require any mid-build deviation to be written back into the spec as a dated amendment — none exists. Solo-start may well be the *right* call for dev/testing, but right now it's a silent divergence exactly the standing rule prohibits. **Fix direction:** either enforce the 2-human minimum or add the dated spec amendment legitimizing 1–4 humans.

- **M4 (MEDIUM): `room.phase` is never set to `'ended'`, leaving dead branches and a comment that describes behavior that cannot happen.** `joinRoom` and `leaveRoom` both branch on `'ended'` (`server/rooms/index.js:90,109,193`) and `leaveRoom`'s doc-comment promises "'left' (lobby/**ended**: slot removed)" — but the only end-of-game path is `loop.js` `onEnd` → `destroyRoom`, which deletes the room outright, so `'ended'` is unreachable. Consequence beyond dead code: post-`GAME_END` sockets are instantly unrouted (`destroyRoom` wipes `socketToRoom`), so there is no post-game room state at all — any Phase 7 "play again / results lobby" flow will collide with this and the taxonomy comment will mislead whoever builds it. **Fix direction:** either delete the `'ended'` branches and fix the comment, or actually transition to `'ended'` before (or instead of immediately) destroying.

- **L1 (LOW): `GAME_END` can report negative hall HP.** `buildEndPayload` uses `Math.ceil(state.hall.hp)` (`server/game/loop.js:84`); a killing blow that takes hp to −3.2 broadcasts `hallHp: -3` to every client's results screen. Clamp with `Math.max(0, …)`.

- **L2 (LOW): client clears a dead reconnect token only when the error message happens to contain the substring "reconnect".** `client/src/network.js:74` — server errors `'Room no longer exists'` and `'Player slot released'` (`server/rooms/index.js:281,283`) don't match, so the stale token is re-sent on *every* future connect, producing an error toast per session forever. Matching UX flows on brittle message substrings is the underlying defect; use an error code field.

- **L3 (LOW): `destroyRoom` never `socket.leave`s survivors — a reused room code would cross-wire broadcasts.** After `GAME_END`, sockets stay joined to the Socket.io room (`server/rooms/index.js:262-275`); the 5-char code returns to the pool. If `generateRoomCode` later re-issues the same code (33⁵ ≈ 39 M — improbable, not impossible, and code churn is attacker-influenceable via C1-style create spam), stale sockets receive the new room's `STATE_UPDATE`/`PHASE_CHANGE` stream: free egress plus another room's state. One loop of `socket.leave(code)` in `destroyRoom` closes it.

- **L4 (LOW): existing clients render a promoted mid-match human as a grey, bot-named dot indefinitely.** `GameScene` builds its roster only from `GAME_START` (`client/src/scenes/GameScene.js:89`) and looks up element/name per snapshot player from it (`:111-112`); `PLAYER_JOINED` (which the server does emit on promotion, `server/index.js:93`) is never consumed by the scene, so the joiner's element color falls back to `0x999999` and the label shows the stale bot name until the viewer reloads. Cosmetic in Phase 1, but the wiring gap is protocol-level and Phase 4 will inherit it.

- **L5 (LOW): the snapshot string is JSON-encoded twice on the wire.** `buildBroadcastSnapshot` returns a pre-stringified payload which the loop wraps in `{ snapshot: payload }` (`server/game/loop.js:59`) — Socket.io then stringifies the wrapper, escaping every quote inside the 3 KB inner JSON, and the client parses twice (`GameScene.js:81`). The packed format is int-heavy so the byte overhead is small (~2-3 %, inside the 1.15 margin), but Spike A's 3,189 B was measured on the *inner* string, so the budget's baseline silently excludes this. Either emit the object and let Socket.io serialize once, or note the wrapper cost in the budget doc.

## Verdict

**CONDITIONAL GO.** The phase machine itself is clean (precedence, boundaries, and timing styles all check out under adversarial tracing), but the room/connection layer has an exploitable availability hole and two bricking paths. **Must fix before Phase 2 builds on this: C1, H1, H3, and M1's `deltaMs` clamp** (C1 is a 3-message full-service DoS; H1/H3 break the basic multiplayer session lifecycle Phase 2+ assumes; the clamp is five lines and closes a whole class of clock bugs). H2 requires, at minimum, a logged measured-cadence check and a written decision before Phase 3 tunes movement/knockback against `TICK_MS`; M2's test-shape fix should land with the next phase-machine change; M3 needs its spec amendment per the standing rule.
