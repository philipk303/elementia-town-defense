### The diagnosis this spec is built on

Three weeks of measurement produced verdicts that moved, got withdrawn, or were
retired wholesale. The causes, in order of damage done:

1. **Nothing persists raw runs.** Every new question requires a full re-run, so
   nobody re-analyses; they re-measure, on a slightly different instrument.
2. **Unstated defaults hide confounds.** The site lists overlapped, the 2-wide
   footprint capped the pool at 8, the free special displaced the Watchtower —
   none of these were visible in any recorded output.
3. **Post-hoc analysis with no multiplicity control.** BH retired 21 of 55
   Welch-significant cells after the fact. The verdicts were being generated by
   the analysis choices as much as by the game.
4. **Under-powered by construction.** sigma ≈ 1.44 on the score metric, so a
   0.5-point effect needs n ≈ 131 — and the power unit on maze A is ~1 SE. We
   are trying to resolve effects at the noise floor with a metric we never
   chose deliberately.
5. **The policy is the confound of last resort.** The Firepit measured 0.073
   targets per pulse — the declared scenario was never delivered, and the score
   measured the build policy, not the structure.

Every element of v2 below targets one of those five.

## 1. Architecture

Four layers, strictly separated. The separation is the point: today all four
live inside each driver script, so you cannot change one without invalidating
measurements taken with another.

```
  L1  SIM ADAPTER      matchRunner.runMatch(protocol) -> metrics
                       (kept as-is; protocol object replaces 13 positional params)

  L2  RUN STORE        append-only JSONL, one line per run, fully-resolved
                       protocol embedded. Never overwritten, never deleted.

  L3  RUNNER CLI       bench/run.mjs — expands a sweep spec into runs, executes
                       across N worker processes, appends to L2, resumes.

  L4  ANALYSIS CLI     bench/analyze.mjs — reads L2 only. Never runs the sim.
                       Refuses to emit a verdict without a pre-registration.
```

The hard rule that makes this work: **L4 never invokes L3.** Analysis is free
and repeatable; measurement is the only expensive step, and it happens once.

## 2. The run record (the contract)

One JSON object per line, in `test/harness/store/<sweepId>.jsonl`.
This schema is the interface between WP1 and WP2 and must not drift.

```jsonc
{
  "schema": 1,
  "runId":      "sha1(configHash + seed + postGap)",   // idempotency key
  "configHash": "sha1(canonicalJSON(protocol) + balanceHash + engineVersion)",
  "sweepId":    "2026-08-16-metric-selection",
  "familyId":   "metric-selection-v1",  // the multiplicity family; see §3
  "armId":      "control",              // human-readable arm label

  "engineVersion": { "gitSha": "06bf64e", "dirty": false },
  "balanceHash":   "sha1 of shared/balance.js bytes",
  "balanceOverrides": { "STRUCTURES.FIREPIT.damage": 60 },  // {} if none

  // FULLY RESOLVED. Every field runMatch accepts is written explicitly, with
  // no default elided. This is the anti-confound rule (cause #2 above).
  "protocol": {
    "mazeName": "A", "seed": 20260801, "postGap": 0, "maxWaves": 10,
    "humanElement": "EARTH", "buildPolicy": "scripted-v1",
    "sitingProtocol": "isolated", "specialSiting": "funnel",
    "fuse": true, "fuseWave": 4, "fuseWith": "FIRE",
    "freeSpecial": true, "defence": "WATCHTOWER", "defenceCap": null,
    "spendDown": false
  },

  "outcome": { "won": true, "lost": false, "stalled": false,
               "timedOut": false, "stoppedEarly": false },

  "metrics": { /* every scalar runMatch produces — score, wavesCleared,
                  hallHpFrac, enemySeconds, playerDowns, playerDeaths,
                  towersPurchased, rebuildsSkippedForGold, goldUnspent,
                  aoeEnemySeconds, peakProjectiles, comboFormed, ... */ },

  "waves":  [ /* the full per-wave record array, verbatim */ ],
  "combat": { /* snapshotCombatStats verbatim */ },

  "durationMs": 312,
  "startedAt": "2026-08-16T09:14:02.113Z"
}
```

**Invariants (enforced by test):**

- Append-only. The runner never rewrites a line. Re-running a sweep appends;
  the analyser dedupes on `runId`, newest wins, and **warns loudly** if two
  records share a `runId` but differ in any metric (that means the engine
  changed under a fixed `engineVersion` — a corruption signal).
- `protocol` round-trips: `runMatch(record.protocol)` on the same
  `engineVersion` + `balanceHash` reproduces `metrics` exactly. A test asserts
  this on a sample of 5 records.
- A run that stalls/times out is **stored, not dropped**. Hang exclusion is an
  analysis decision (L4), never a measurement decision (L3). This is what makes
  hang-imputation sensitivity free to compute.

## 3. Pre-registration (the discipline fix)

A sweep cannot be analysed without a committed pre-registration file at
`test/harness/prereg/<familyId>.json`:

```jsonc
{
  "familyId": "fusion-roster-v2",
  "question": "Does any fusion clear the A1.4(a) niche floor on either maze?",
  "primaryMetric": "score",           // exactly ONE
  "secondaryMetrics": ["enemySeconds", "wavesCleared"],
  "mde": 0.5,                         // declared BEFORE the run
  "alpha": 0.05, "power": 0.80,
  "sigmaSource": "2026-08-16-metric-selection corpus, score sigma = 1.44",
  "nRequired": 131,
  "arms": ["control", "firestorm", "blizzard", "..."],
  "mazes": ["A", "B"],
  "familySize": 12,                   // cells the BH correction spans
  "decisionRule": "PASS iff paired t is significant at BH-adjusted q<0.05 AND the exact sign test agrees AND split-half rho > 0.5 AND the verdict survives hang-imputation at the cell minimum AND it holds under both build policies (WP5).",
  "whatWouldRefute": "A delta whose BH-adjusted q exceeds 0.05, or a sign flip between the two build policies."
}
```

`analyze.mjs` behaviour:
- No prereg file for a `familyId` → **refuse to print a verdict.** Print raw
  descriptives only, banner-tagged `EXPLORATORY — NO VERDICT`.
- Any metric or cell analysed that is not in the prereg → same tag, per-row.
- Every verdict line prints raw p **and** BH-adjusted q side by side, always.
- If **fewer** tests actually ran than the declared `familySize`, the BH input
  is padded with `p = 1` up to `familySize` rather than corrected over the
  smaller set. (Proposed by the WP2 agent, adopted 2026-08-14.) Correcting over
  what you ended up running lets a family silently narrow its own correction
  after seeing results — which is the post-hoc move that retired 21 of 55 cells
  the last time it went unchecked. Padding makes the declared family binding.
  If **more** tests ran than declared, that is a spec violation and the family
  is reported as such, not quietly re-corrected.

This directly answers cause #3 and the "verdict moved three times" failure.

### WP3 — protocol-object refactor (Claude, first)

Replace the 13 positional params of `runBuildPolicy` with a single frozen,
fully-resolved `protocol` object built by an exported `resolveProtocol(partial)`
that **writes every default explicitly and throws on any unknown key**.

- Retire `funnelSites`/`towerSites`/`offLaneSites` from the live path. The
  isolated protocol becomes the only protocol. Legacy lists move behind
  `protocol.legacySiting: true`, used **only** by the pinned tests that
  reproduce historical measurements.
- `walkableDefenceSites` stays (it is a genuine capacity fix, not a confound).
- Add an assertion at build-policy exit: **the actual placed footprints are
  recorded into `metrics.placements`** (type, gx, gy, w, h). The watchtower
  displacement confound would have been visible in one glance at this field.
- Acceptance: `npm test` green; `matchRunner.test.js` pins unchanged behaviour
  under `legacySiting: true`.

### WP4 — empirical metric selection (Claude, the payoff)

Once the store exists, this is nearly free and it is the answer to cause #4.
From ONE corpus of ~4000 runs (est. ~20 min on 4 workers at ~0.3 s/run):

1. Compute, for every candidate outcome metric, its within-cell sigma, its
   paired sigma, and therefore its MDE at n=144.
2. Candidates: `score` (today's), `wavesCleared`, `hallHpFrac`,
   `enemySeconds`, per-wave `structuresLost`, `closestApproachPx`, an
   AUC-of-hall-HP-over-waves, and a censoring-corrected clear margin.
3. Check each against the criterion that matters: does it order arms the same
   way `score` does (split-half rho) *while* having a smaller MDE?
4. **Adopt the lowest-MDE metric that preserves ordering, and record the
   choice in a prereg.** If none beats `score`, say so and raise n instead —
   the sim is cheap and CPU is the correct thing to spend here.

### WP5 — policy sensitivity (Sonnet)

The scripted human is deliberately dumb, and at least one published verdict was
a measurement of the policy. Build a second policy, `competent-v1`: repositions
between lanes, prioritises rebuilds by band, does not blindly hold every button.
**Rule: no verdict ships unless it holds under both policies.** Disagreement is
itself the finding — it means the number is a policy artifact.

### Dispatching to Codex — a note that cost two runs

`~/.codex/AGENTS.md` line 99 carries a global "before executing any large
coding task, ask what else to include and wait for confirmation" rule. Both WP1
and WP2 obeyed it, produced a design, and stopped without touching the repo.
The reading and design work was good — WP2's proposal is the source of the BH
padding rule above — but the runs did nothing.

Dispatch through **`tools/codex/dispatch.sh`**, which prepends the
authorization preamble mechanically rather than relying on whoever writes the
next brief to remember it:

```
tools/codex/dispatch.sh <brief.md> [--model gpt-5.6-sol] [--effort high]
```

It prints the session id and the exact resume command on exit. Prefer
`codex exec resume <session-id>` over a fresh dispatch when an agent stops
anyway — the design context is worth more than the retry. WP2 was resumed and
its design survived; WP1 was re-dispatched and its 21k tokens were lost.

Editing `~/.codex/AGENTS.md` to scope the rule was considered and declined
(Philip, 2026-08-14): the rule is right for interactive Codex, and the fix
belongs on the dispatch side rather than in a global config that reaches every
project.

## 5. Explicitly out of scope

- No new game-balance changes until WP4 lands. Every tuning decision taken on
  the old instrument stays reverted/frozen.
- No re-litigating the Firestorm magnitude, the siting ruling, or the
  Magma Trap verdict. They get re-measured on v2 or not at all.
- No GUI/visualisation. Text tables until the numbers are trustworthy.

## 6. Success criteria

The harness is done when all five hold:

1. Any past verdict can be re-analysed from the store without re-running.
2. Every published number carries a BH-adjusted q and a declared MDE.
3. A deliberately-injected balance change of exactly the declared MDE is
   detected by the harness (a **positive control** — the thing the 2026-07-25
   review flagged as missing and that still does not exist).
4. Two independent build policies agree on the sign of every shipped verdict.
5. A full roster sweep is one command and its output is a committed artifact.

Criterion 3 is the one that has never been met. Until an injected known effect
is recovered at the declared size, the instrument is unvalidated.
